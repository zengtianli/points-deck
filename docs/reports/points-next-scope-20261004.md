## 后续顺序与终点

1. 先修会阻塞本次交付的范围选择和总时限；依赖登记仅改证据能支持的部分，不开展跨项目缓存重构。只做对应参数、等待／超时、跳过逻辑的窄验证。
2. Web 先给与原生对照的一个可看页面，再铺到相关页面；完成五栏目和核心操作的一致性检查。不重新测已完成 Apple 平台。
3. 账号完整闭环仍是 PRD P0。短信真实投递和原生所有账号变更表单的缺口如实保留，沿已有服务与安全配置处理，不用测试替身冒充生产通过。
4. 每阶段写清结果、时限、剩余工作和停止条件。阶段预算与产品总耗时同源累计，等待和收尾计入；超时先交有效产物与具体卡点，不静默新增阶段，不把未完成报成完整通过。

## 本轮已落实

- 测量入口必须提供 `--only`／Chapter 的 `SOP_PERF_PLATFORM`，整批须显式 `--all`；同输入继续跳过，首个失败／推迟立即结束。iPad 不再固定多等 600＋300 秒，准备等待可配置。
- 三个原入口均增加从入口起算的 `--budget-min`；有界获取原锁，剩余预算约束命令并留清理时间。超时退出 75，仅结束本次创建的进程组。隔离服务器启动后立即记所有权，初始化途中被中断也可收回。
- UI／截图增加显式 `--functional-only`：原准入一次检查，忙即推迟；截图只取五个核心视图，省资源基线和额外屏幕尺寸。默认完整模式仍沿原门，不降低阈值或绕锁。
- Web 三页共享原生主题，五栏与手机底部导航一致；加减分分段、奖励可键盘点击、手机流水卡片；复用原 API 和账号。Chrome 隔离账本实测与后端读回；318 个后端检查和 8 个入口回归通过。
- 未改其他 Codex 占用的 Chapter、HARNESS、skills。平台依赖输入收窄尚未修改：当前平台缓存与原证明绑定旧范围；不借修登记启动新一轮全端工作，也不把旧 PASS 重写到新摘要。

本轮终点：以上脚本及本地 Web 修复、窄验证与可看的汇报。不公开部署或推送，不重跑 Apple 平台。生产短信投递、完整网页项目管理和商店审核仍按原缺项记载。原件见 `points-fixes-20261004.validation.json`；预览仅本机隔离测试数据。
